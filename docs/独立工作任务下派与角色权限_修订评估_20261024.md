# 独立工作任务下派与角色权限：修订评估

日期：2026-10-24。

## 1. 修订结论与业务边界

本功能定义为独立的“工作任务”模块，承载日常工作交办、员工评估、时间节点承诺、执行反馈、成果提交、验收及分角色日终汇总。

- 不要求关联项目，不使用项目编号作为任务归属。
- 不扩展 ProjectTaskEntity 或把 ProjectFile 作为工作任务附件表。
- 不使用项目负责人决定谁有下派、验收或查看权限。
- 原项目管理、项目任务看板、甘特图和相关 Agent 工具保持原业务边界。
- 继续复用统一登录、账号标识、可通用化的文件组件，以及现有微信/邮件发送通道。
- 业务独立不等于另建一套登录账号，也不要求另部署一套前后端。

原《工作任务下派与日终同步_功能评估_20261024.md》中挂靠项目的建议不再适用。

## 2. 成熟方案的借鉴方式

采用“业务角色 + 范围授权 + 单条任务关系 + 流程约束”的权限方式。

- RBAC 用角色组织功能权限；管理层级与职责约束需要明确建模，不能只靠角色名称。参考 [NIST RBAC 说明](https://csrc.nist.gov/Projects/Role-Based-Access-Control/faqs)。
- 成熟任务产品还使用对象级访问控制：参与一条任务并不等于能查看其他任务。参考 [Asana 权限概述](https://help.asana.com/s/article/permissions-overview)。
- 飞书的派发/跟进/审核、Asana 的提交审批，以及 Jira 的事件/定时通知模式仍可借鉴；不继承这些产品的项目权限模型。

下述角色与规则是结合当前系统提出的设计建议，不代表现有代码已经具备。

## 3. 重新划分工作任务业务角色

建议一期采用四个工作任务业务角色，平台系统管理员继续作为平台角色单独存在。

| 角色 | 默认职责 | 默认业务边界 |
|---|---|---|
| 执行员工 | 查看分配给自己的工作、回复评估、承诺节点、更新进展、上传成果和提交验收 | 办理自己主责的任务；参与其他任务时按该任务授予的权限协作 |
| 派发主管 | 编辑/下派任务、确认评估排期、处理延期、按指定身份验收及查看管理摘要 | 仅在被授权的工作组/人员范围内下派；不是所有主管都能处理所有任务 |
| 督办人员 | 查看授权范围内的执行状态、逾期与阻塞，催办和形成管理汇总 | 默认没有代员工提交成果、改写承诺节点或直接验收的权限；需要办理时另授相应角色及任务身份 |
| 工作任务管理员 | 配置工作组、模块业务授权、流程规则、日终时间及通知模板；按授权处理异常交接 | 管理模块不自动获得所有任务正文、成果和验收权；业务查看/代办需另行授权并留痕 |
| 平台系统管理员（已有） | 账号、登录、应用准入、平台运维 | 不把平台管理角色自动等同于任务主管；如保留超级管理员应急访问，必须明确例外范围与审计 |

同一用户可拥有多个业务角色，但每份角色授权必须同时绑定适用范围。例如“维修组主管 + 生产组执行员工”不能组合成“生产组主管”。

不建议按总经理、部长、科长、班长等每种职称重复建立功能相同的角色。职务和管理层级用组织关系表达，业务角色表达实际操作能力。

## 4. 管理关系与数据范围

当前账号模型已经有角色、权限键；应用授权也已有项目、线体、设备等范围，但这些范围不适合直接表示工作任务的上下级管理关系。

建议增加轻量的工作组织关系：

- 工作组/部门：名称、负责人、成员、可选上级工作组。
- 人员管理范围：可以对哪些成员下派任务、查看哪些组织层级的任务、是否允许跨组派发。
- 汇报关系：员工的主要汇报负责人，以及必要的业务管理负责人。
- 业务角色授权：用户、角色、授权范围、有效期、授权来源和审计信息。

管理范围应明确选择“本人相关、直属成员、本工作组、包含下级工作组、指定工作组/人员、明确授予的全模块范围”。本组与包含下级不能隐式混用。

若一期尚不需要完整公司组织树，可先用“工作组 + 负责人 + 成员 + 指定管理范围”，后续再接正式部门层级。

跨组派发需要显式授权；允许选择的收件人必须来自后端返回的可派发人员范围。不能通过修改请求中的 UserId 绕过选择范围。

## 5. 单条任务的身份关系

每条工作任务独立保存以下身份：

| 身份 | 作用 |
|---|---|
| 创建人 | 谁编辑了草稿，保留来源记录 |
| 下派人 | 谁正式交办并承担后续跟进责任 |
| 主责人 | 谁评估、承诺节点并提交最终成果 |
| 验收人 | 谁审核这一条任务的成果；默认可带入下派人，但必须具备验收权限 |
| 汇总负责人 | 谁接收该任务的管理摘要，可由组织规则给出默认值 |
| 协作人 | 按授予权限补充进展或材料，不自动获得主责人的最终提交权 |
| 关注人 | 查看获准内容和接收相关变化通知，不获得修改和验收权限 |

协作人与关注人是单条任务的身份，不必再建立成全系统业务角色。

有验收能力不等于可以验收任意任务：必须属于授权范围，并且是当前有效验收人。主管同时作为某条任务执行人时，默认由另一位有权限人员验收，不能利用多角色给自己验收。

## 6. 推荐的操作矩阵

“允许”仍需满足应用准入、授权范围、任务关系和当前流程状态。

| 操作 | 执行员工 | 派发主管 | 督办人员 | 工作任务管理员 |
|---|---|---|---|---|
| 创建并正式下派工作 | 默认否 | 授权范围内允许 | 需另有派发角色 | 需另有派发角色 |
| 回复评估、承诺时间节点 | 当前主责任务 | 自己承担执行任务时 | 自己承担执行任务时 | 自己承担执行任务时 |
| 确认排期、延期 | 提出申请 | 当前下派/负责且有权限的任务 | 默认只查看、催办 | 仅按异常处理授权操作 |
| 上传最终成果、提交验收 | 当前主责任务 | 自己承担执行任务时 | 自己承担执行任务时 | 自己承担执行任务时 |
| 验收通过/退回 | 默认否，需另授验收能力并指定身份 | 当前被指定验收且非自验收的任务 | 默认否 | 默认否 |
| 查看团队任务及管理汇总 | 默认仅个人相关 | 授权管理范围 | 授权督办范围 | 另授业务查看范围 |
| 催办 | 可向相关责任人反馈问题 | 授权范围 | 授权范围 | 按授权范围 |
| 配置组织、业务授权及规则 | 否 | 默认否 | 默认否 | 允许，但不能超出自己可委派的权限 |

多角色授权是“角色与范围成对的权限”组合，不是把所有角色的操作和所有组织范围任意交叉组合。

平台账号拥有 `*`、旧管理员角色或 AllResources 时，也不能通过普通任务接口绕过自验收、流程状态等职责限制。平台应急权限如确实需要，作为单独且可审计的机制设计。

## 7. 独立任务流程

```mermaid
flowchart LR
  A[草稿] --> B[已下派：待评估]
  B --> C[员工回复评估与节点]
  C --> D[执行中]
  C --> G[排期待确认]
  G --> D
  D --> E[上传成果：待验收]
  E --> F[验收通过：已完成]
  E -->|退回并说明原因| D
```

- 一个工作任务明确一个主责人；多人独立承诺和交付时生成独立任务或子任务，不引用项目任务关系。
- 设置评估回复期限，分别记录下派要求时间与员工承诺时间。
- 超出要求的排期进入确认；延期保留原节点和变更原因。
- 提交与验收分开；进度 100% 不直接改为已完成。
- 逾期、阻塞、评估超时和验收超时作为各自提示，不覆盖主状态。
- 员工按时提交后等待验收，不把等待领导审核的时间继续计为员工执行逾期。
- 转派、取消、重新打开、代理办理等动作记录操作者、原因和版本。

## 8. 日终同步与角色联动

工作组可配置下班时间、提前多久同步、工作日历和渠道。先按业务日期和固定截点生成摘要，再根据权限分别渲染。

| 接收角色/身份 | 摘要范围 | 重点内容 |
|---|---|---|
| 执行员工 | 本人主责或明确授权参与的任务 | 待评估、今日/明日节点、待补充、被退回、今日提交和验收结果 |
| 派发主管 | 本人下派及明确授权管理的任务，汇总时去重 | 未回复评估、未确认排期、待验收、逾期、延期、阻塞和需协调事项 |
| 督办人员 | 授权督办范围 | 团队/工作组总体进展、异常分布、反复延期和催办记录，不代替验收人办理 |
| 模块管理员 | 自身业务角色获准的内容；另有技术运行报表 | 通知失败、调度漏发及配置异常，业务内容可见权独立判定 |

同一个人既是主管又是执行员工时，管理摘要和个人摘要各有明确类型，可以分开推送，也可合并为一条分区消息，内容按各自权限生成，避免混淆。

任务的实际汇总负责人应持久化记录；组织默认值用于创建/交接。人员调岗、上下级变化不能无记录地把历史任务和旧日报自动交给新领导。当前操作与投递仍按最新有效授权复核。

不能根据“拥有主管角色”直接向其推送全体员工任务。消息正文、通知详情链接、文件预览和下载均使用同样的任务授权规则。

推送继续采用事件入库、摘要快照、投递去重、失败记录和可控补发；即时通知与日终摘要分开。

## 9. 在当前前后端中的实现边界

建议独立建立 `/api/work-tasks` 接口、`work-tasks` 前端目录及 WorkTask 领域表。可按职责分为：任务、人员关系、评估/节点、进展、成果提交、附件、验收、操作记录、通知事件、日报和投递关联。

组织/业务角色授权另建工作任务范围表，不把权限塞进项目、线体或设备授权字段。

复用范围：

- 统一账号与登录、现有菜单及角色管理基础界面。
- 通用文件选择、预览组件，以及独立存储目录或可抽取的文件服务。
- 微信 ClawBot、邮件队列及发送记录；新增工作任务通知来源和模板。
- 日志、数据库基础设施和后台 Worker 部署方式。

必须新增或改造：

- 模块专属业务角色、组织/人员范围与统一授权策略。
- 工作任务状态机、节点承诺、提交/验收记录与版本冲突控制。
- 独立附件表和文件归属，上传者从当前登录身份确定。
- 不同角色的待办视图与日报查询，避免先查全量再在前端过滤。
- 后台通知身份与业务授权，发送前再次检查人员停用、转派、撤权和渠道可用性。

现有 A/B 应用准入可以继续复用；工作任务在 A/B 间共享还是隔离，应作为单独业务口径决定。不能因为账号相同就默认互通，也不能把“业务独立”直接理解为第三套账号体系。

## 10. 推荐的一期范围和验收重点

一期完整实现：四类工作任务角色、工作组与人员授权、下派评估和节点、执行反馈、文件/图片成果、指定验收、领导与员工日报、即时通知、失败与补发记录。

重点验收：

1. 员工只办理自己获准的工作，替换任务 ID、收件人或附件 ID 不能越权。
2. 同角色的两名主管不会自动看到或修改对方管辖任务。
3. 上级查看下级范围和跨组派发只有显式授权时成立。
4. 多角色用户不会扩大其他工作组的管理权限，也不能自行验收。
5. 协作人只看到被加入的任务，不能扩展为整个工作组可见。
6. 员工改节点、提交成果、主管验收均受状态与版本校验。
7. 转派、调岗、离职/停用及代理办理的当前权限与历史记录一致可追溯。
8. 领导、督办、员工的摘要范围准确，不通过消息或附件链接泄露其他任务。
9. 多实例、重启、重试不重复生成任务通知或日报投递。
10. 原项目管理的角色、菜单、任务状态及附件保持原业务语义。

实施前仍需确定：组织/工作组层级、是否允许跨组或越级下派、验收人选择规则、A/B 共享口径、推送渠道及下班时间。本稿只完成修订评估，不执行角色重分配、数据库修改或真实任务派发。

## 11. 个人 MCP 自助汇报扩展

后续增加了个人密钥接入、查询本人任务及文字/图片/文件汇报的需求，参见《独立工作任务_个人密钥MCP汇报接入评估_20261024.md》。MCP 是本模块的另一个办理入口，沿用这里的角色、范围、任务关系与流程约束，不继承现有匿名直连 MCP 的全资源访问模式。
