# 设备卡片字段微信推送

日期：2026-10-09。新增迭代说明，不覆盖以前的 MD。

## 使用入口

后台「设备卡片配置」→ 编辑卡片 → 字段表格「数据推送 / 设置」。这是原配置页面的扩展，不需要新增菜单或动态路由。

1. 选择该字段是否启用推送，以及「本系统微信」或「外部 MCP」负责人。
2. 微信接收人可搜索、多选，关联后台用户的微信绑定。
3. 选择字段变化、超过上下限、恢复正常；上下限在字段行维护。
4. 配置推送变化阈值、变化消息间隔、消息模板。
5. 点击「应用到表单」，再点击卡片「保存」，才会持久化。
6. 可点击「测试推送」。首次配置需先保存卡片及字段推送配置。测试读取后端该设备字段的实际最后已知值，接收人与模板使用当前弹窗选择，不发送占位数据。
7. 配置页面工具栏「字段推送记录」可筛选接收人和状态、展开消息正文、查看尝试次数与失败原因；弹窗打开时每 3 秒刷新。

接收人必须是启用的后台用户，已绑定微信且未被管理员禁用推送。会话未就绪仍可配置，但用户需要先在微信向 ClawBot 发一条消息建立会话；没有会话时任务显示「暂不可发送」。

内部卡片通知不借用 `McpPushEnabled` 外部 MCP 授权开关；仍尊重用户启用、微信绑定和管理员禁用状态。接收人接口不返回 bot token、会话 token 或微信内部收件标识。

## 触发规则

- 推送独立于追溯：没有勾选追溯，也可以配置变化推送。
- 初次明确上报只建立基准，默认不通知，包括第一次就越限的情况。
- 缺失字段不触发通知，也不借其他设备的样例填值。
- 明确 `null` 默认不通知，且不当成恢复正常；重新收到正常数值后才判断恢复。
- `0`、`false` 和空字符串是实际值；文本/布尔变化不使用数值阈值。
- 配置为数值类型的字段也兼容 `"25.5"` 这类数字字符串，与现有上下限校验保持一致。
- 数值变化相对于上次推送基准累计比较，达到配置阈值才推送。阈值留空或 0 表示实际数值变化即触发。
- 上下限为严格越界：低于下限、超过上限。等于上下限仍正常，与现有越限逻辑一致。
- 持续处于同一越限状态不会每帧通知；上下限之间切换、从越限恢复可产生新的事件。
- 同一帧既越限又满足普通变化时，优先只发越限/恢复通知，不重复发变化通知。
- 变化推送间隔默认 300 秒，范围 0～86400 秒，仅抑制普通变化消息，不抑制越限和恢复事件。
- 更换设备模型或修改推送配置后重新建立基准，避免把不同设备/规则的旧状态当新事件。

模板变量：`{event}`、`{line}`、`{device}`、`{field}`、`{oldValue}`、`{value}`、`{unit}`、`{lower}`、`{upper}`、`{time}`。`device` 为卡片名称，`line` 为线体编码；值是该字段实际原值，时间是字段实际数据时间。

留空使用默认模板。模板最多 2000 字；生成的内容超过微信适配层的 10000 字限制时截断并说明。模板仅进行受控字符串替换，不执行表达式、代码或 URL。

## 后台链路

HTTP 实时接收的同一个数据库事务中保存：原始报文、字段最新值、推送检查点和每位接收人的任务。任何一步失败一起回滚，上报方可重试，不会出现只存数据却丢掉推送任务的中间状态。

接收过程不请求微信、不调用大模型。后台发送服务延迟 30 秒开始工作，每次最多取 20 条任务，顺序发送，空闲间隔 3 秒。它只是发送队列处理器，不是新增周期查询设备的计划任务，也不引入 Redis。

发送前重新检查卡片、字段、规则、接收人和用户启用状态。停用或修改规则会取消尚未开始的旧任务。已进入网络发送的消息无法撤回。

任务固定到创建时的微信绑定标识；用户换绑到其他微信会话后，旧任务取消，不自动改投新绑定。收件用户名保留为任务快照，解绑后历史记录仍可识别人。绑定指纹仅后端使用，不经 API 返回。

## 数据库

中心业务数据库新增四张表，实体均使用 SqlSugar 初始化。

| 表 | 用途与唯一约束 |
| --- | --- |
| EdgeDeviceCardPushRule | 字段推送规则；CardId + FieldCode 唯一，字段表编辑重建不改变关联 |
| EdgeDeviceCardPushRecipient | 规则对应的多位后台用户；RuleId + UserId 唯一 |
| EdgeDeviceCardPushState | 最后实际值、变化基准、越限状态和源时间；RuleId 唯一 |
| EdgeDeviceCardPushTask | 每个事件的每位接收人一条任务；EventKey + UserId 唯一，保存消息、结果、次数和投递日志关联 |

时间与可空字段显式声明 SQL NULL；未发送、没有认领等状态不填虚假时间。主键为数据库自增。新表在启动阶段初始化，不在接收人/任务查询中执行 CodeFirst。微信依赖表也复用现有初始化器在启动阶段完成结构初始化与旧可空列修复，不在启动阶段发微信网络请求。

保存客户端没有传 `Push` 时保留既有推送配置，避免旧 Agent/客户端编辑其他字段时静默关闭通知；新字段默认关闭。

本期没有自动删除推送历史的策略。记录仅按符合条件的事件产生，不是逐帧存储；保留时长可在后续迭代单独配置。

## 状态、重试与防重复

| 状态 | 含义 |
| --- | --- |
| Pending | 等待后台发送 |
| Processing | 原子认领后发送中 |
| Sent | 微信接口已确认接受，不代表用户已经阅读 |
| Retrying | 明确失败后等待下一次尝试 |
| Failed | 明确失败且达到自动尝试上限，可人工重试 |
| Blocked | 用户/绑定/会话暂不可用，不自动反复请求微信；修复后可人工重试 |
| Unknown | 网络中断、超时或发送过程中进程中断，无法确定是否已经送达，不自动或盲目人工重发 |
| Cancelled | 原配置、接收人或绑定已变化，任务取消 |

明确失败最多自动尝试 3 次，间隔 30 秒、120 秒。人工重试继续增加尝试次数并保留审计。每次尝试有独立幂等键，同一尝试复用既有投递记录。

任务认领使用数据库条件更新，多个后台处理器不会同时认领同一条任务。认领有效期为 5 分钟；重启后过期的 Processing 标成 Unknown，不退回 Pending 重发。发送超时、传输中断、无法确认响应、HTTP 5xx 等不确定结果保留 Unknown，而不是当成确定失败自动重试。

网络系统无法承诺用户端“绝对只收到一次”；本实现选择不自动重发不确定结果，降低重复通知风险。Unknown 需要人工核实微信收件情况。

## 与 MCP 的关系

- 本系统微信负责的字段，新越限事件标为 `Internal`，不进入既有 MCP 的 Pending 认领队列。
- `Internal` 表示由系统通知配置负责，不代表每个接收人都已成功，实际结果查看字段推送记录。
- 外部 MCP 模式不产生本系统微信任务；原有越限 Pending / 认领 / 确认流程保留。
- 外部智能体通过已有字段、变化记录、告警工具读取数据并自行调度；需要读取变化记录时另行开启追溯。
- 本轮未新增 MCP 工具或外部定时计划。旧历史告警不做自动改写，切换负责人后应检查旧待办，避免外部之前已经认领的事件仍自行推送。

## 接口

均在后台登录鉴权下，与现有卡片配置接口保持一致，不开放给免登录公开看板。

- `GET /api/EdgeGateway/dashboard/device-card-push/recipients`
- `GET /api/EdgeGateway/dashboard/device-card-push/tasks`：current、size、lineCode、cardId、status、userId。
- `POST /api/EdgeGateway/dashboard/device-card-push/test`：cardId、fieldCode、recipientUserIds、messageTemplate。
- `POST /api/EdgeGateway/dashboard/device-card-push/tasks/{taskId}/retry`
- 卡片原保存/回读接口，展示字段增加可选 `push` 对象。
