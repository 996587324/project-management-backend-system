# 独立工作任务与个人 MCP：产品与架构复审意见

日期：2026-10-27。依据：[2026-10-26 改造设计评审稿](独立工作任务与个人MCP_改造设计评审稿_20261026.md)。

状态：补充评审建议，未获业务定稿，未实施。本次保留原稿，仅新增本文件；未改业务代码、数据库、运行服务或 Git 远程版本。

## 1. 复审结论

原稿的技术方向可保留：独立工作任务、复用现有账号、网页与个人 MCP 共用服务、独立业务权限、复用消息通道、可靠记录业务变化。

本轮建议把重点从“页面、接口和表是否齐全”转向四个问题：

1. 员工是否明确知道做什么、何时交付、什么条件算完成。
2. 员工能否用较少操作完成评估和汇报，领导能否及时处理协调、延期和验收。
3. 同一件事经过修改、转派、重试、跨端办理后，记录和统计是否仍可信。
4. 新任务内容经过消息队列、附件、日志和外部客户端后，是否仍遵守原定权限。

建议继续开发现有前后端内的模块，当前没有必要引入微服务、流程引擎或新消息中间件。原稿的 18 张表是讨论起点，不应作为必须达到或不能超过的数量。

## 2. 从产品经理角度需要调整的内容

### P01：下派任务时补齐“交付标准”

原稿已有要求和交付说明，但还需要把“完成标准”作为可评审的业务规则。

- 下派内容至少包括目标、主责人、交付标准、时间要求／由员工评估排期、需要的成果形式。
- 成果形式可选文字、图片、文件或组合；附件不是所有任务的必填项。
- 如果启用验收，明确验收人、退回原因和待验收提醒规则。
- 员工评估时能提出问题或说明无法承担，不能只有“接受”按钮。

例如，“排查某设备异常”应说明预期交付是原因说明、处理记录或现场照片，而不是员工传任意一张图片就能结单。

### P02：采用轻量流程，保留正式责任节点

建议普通任务只需一次评估和一个承诺完成时间，复杂任务才增加多个节点。

- 主状态保持少量：草稿、待评估、执行中、待验收、已完成、已取消；免验收任务按选定规则跳过待验收。
- 阻塞、逾期、排期待确认作为标记，不扩展为大量互相排斥的主状态。
- “待补充”明确指向哪次退回／缺少什么材料，不成为一个没有责任人的笼统状态。
- 评估、排期确认、验收分别明确当前待办人和处理期限；不能只考核员工交付时间。
- 正式任务增加取消原因；完成后的再次处理采用明确的重开或关联后续任务规则，一期可以先采用新建关联任务。

是否必须验收、哪些排期需要批准，仍属于待确认事项；不因本轮建议自动变成强制要求。

### P03：区分原承诺、当前承诺和最新预计

原稿保留排期版本的方向正确，但还需补充统计规则：

| 时间 | 含义 |
|---|---|
| 要求时间 | 下派方期望，可能标记为由员工评估 |
| 首次生效承诺 | 员工首次被确认的交付承诺，作为原始基准保留 |
| 当前批准承诺 | 经合法变更后正在生效的承诺 |
| 最新预计完成 | 员工对实际进展的预测，更新预测不自动修改承诺 |
| 实际提交／验收时间 | 两个不同事件，分别记录 |

延期批准后，界面可以按新日期安排待办，但报表仍展示原承诺、延期次数和原因，避免通过反复修改日期掩盖延期。员工按时提交、领导迟验收，也不能直接算员工交付逾期。

### P04：日终汇报尽量自动生成，补充信息按需填写

建议由系统从当天已有的评估、节点、进展、阻塞、提交和验收中生成摘要，不再要求员工重复填一份内容相同的日报。

- 员工可补充“今天的说明／明天计划／需要支持”。
- 没有新记录应展示“今日未更新”，不能生成“今日无进展”或虚构成果。
- 领导优先看到待协调、待批准、待验收、即将到期和逾期事项，附可直接处理的链接。
- 员工优先看到本人待办、承诺节点和被退回内容。
- 空摘要可以不发送；有阻塞、到期或待处理事项时仍应提醒。

员工接收范围仍需确认。建议覆盖有待办、当天变化或近期到期事项的员工；如果业务选择仅发给当天完成人员，需接受其他员工不能靠该摘要获得待办提醒的结果。

### P05：补充业务待办与任务讨论，减少通知噪音

建议“我的工作”直接承载站内待办；外部消息用于提醒，员工不绑定微信／邮件也能办理任务。

- 区分消息已发送、已读、任务已评估、已提交、已验收，不能混为一个“已完成”状态。
- 支持简单的任务问答／意见记录，员工可以询问要求，主管可以答复；不必建立即时聊天系统。
- 一期讨论默认对获准任务参与者可见；如果要领导内部备注，应另定可见范围，不能默认混入员工／MCP 返回内容。
- 催办设置间隔和合并规则，不把每次自动保存都变成外部通知。

### P06：明确管理交接，避免任务失去处理人

需要覆盖员工离职／停用、领导调岗、验收人请假、工作组调整。

- 有未结任务时展示影响清单，由获准人员明确交接。
- 指定代理人的授权带范围和有效期，不因组织层级变化就自动把全部历史材料开放给新领导。
- 区分“任务固定汇报负责人”和“组织关系提供的默认负责人”；组织变化后的未结任务走明确交接。
- 原执行人留下的记录和责任不被新执行人的身份覆盖。

一期无需建设完整人事系统；先用轻量工作组和显式交接满足上述场景。

### P07：压缩菜单层级，补齐员工实际操作体验

建议顶层聚合为“我的工作、团队工作、工作设置”；下派、验收和成果处理作为相应页面的标签或详情操作。个人凭证放个人中心入口。

- 员工首页直接显示“接下来需要我处理什么”。
- 手机浏览器能查看详情、填写说明、选择照片和上传文件；这属于员工使用链路，应纳入验收。
- 服务端自动保存草稿并显示保存状态；结合已有 20 分钟空闲退出，在登录失效后重新登录可恢复已保存内容。自动保存和 MCP 轮询不算用户操作，不因此续期网页会话。
- 上传显示进度、失败原因和重新上传入口；正式提交前明确展示本次文字与材料。
- 一期无需承诺原生 App、离线同步和复杂协同编辑。

### P08：把“人员负荷”改为有依据的指标

原稿出现“人员负荷”，但未定义预计工时、可用工时和排班。仅靠任务数量不能推断真实负荷。

一期建议展示在办任务数、近期到期数、阻塞数、待验收数和最长待处理时长，名称与实际口径一致。预计工时与容量规划可后续另行评审。

衡量本功能是否有用，优先观察评估及时性、正式提交及时性、领导处理等待时间、退回原因和通知可达情况；一期不据此自动计算员工绩效或排名。

## 3. 从架构师角度需要调整的内容

### A01：先确定任务归属，再决定 AppCode 是否足够

原稿暂按 A/B 隔离，属于待确认的设计假设。需要先明确 A/B 是两个业务空间，还是同一工作业务的不同入口。

- 若确实独立，沿用 `AppCode` 隔离即可。
- 若要求同一条任务从 A/B 都能进入，应建立明确的工作空间归属与应用访问映射，任务属于工作空间，入口按授权访问。
- 同一账号在两个入口登录，不意味着两边任务可自动互见。

不建议现在为了预留多租户建设复杂平台，但数据归属必须在建表前明确。不能上线后仅去掉 `AppCode` 条件实现共享。

### A02：维持同一后端部署，模块内部明确职责

建议分成工作任务、组织授权、附件、个人接入、通知作业几个职责清楚的组件，由统一业务命令处理流程。

```text
网页接口／MCP 适配
         ↓
统一操作者上下文 → 授权检查 → 业务命令与状态转换
                                   ↓
                     SQL 事务：业务记录＋版本＋回执＋待处理事件
                                   ↓
                         后台通知处理 → 现有通道
```

控制器和 MCP 工具都不能直接更新任务状态；它们只调用同一个业务命令。后台调度与 HTTP 请求各自建立服务作用域，不长期持有请求身份或数据库上下文。

### A03：补齐可还原的要求版本和附件关联

原稿提出正式要求变更和提交版本，但列出的表还需要细化：

1. 增加完整的任务要求版本存储，例如 `work_task_revision`，记录当时的要求、时间、主责、交付标准与生效关系。审计摘要不能替代完整历史要求。
2. 正式提交明确关联它依据的要求版本、排期版本、提交版本和附件集合；验收针对同一固定提交版本。
3. 文件元数据与业务关联分开。建议显式附件关联记录，或采用同等约束的结构；不能仅保存一个允许客户端随意替换的附件 ID 数组。
4. 简单评论可作为有明确类型的追加记录；是否与进展表共用物理表在详细设计中决定，可见性与作者信息不能省略。

表数量可据此调整。正确的关系、历史和约束比坚持 18 张更重要，也无须因此引入全量事件溯源架构。

### A04：业务事件与通知投递分开建模

原稿把业务事件和派生投递放在一个 `work_task_outbox` 逻辑表中，建议拆清生命周期：

- 业务事件：一次任务事实，例如成果已提交；事件内容固定，记录处理状态。
- 通知投递：此事件应通知哪些人、使用什么通道、是否入队／失败／待核实，可产生多条。
- 日终快照：某个截止时点、某个人和视角的摘要内容及版本。

物理上可新增投递关联表，通道发送状态继续复用现有微信／邮件表；不应再造第二套通道重试队列。

业务变化和事件同事务提交，异步派发采用去重与重试，不承诺外部消息绝对只到达一次。此处采用通用事务 Outbox 思路，参考 [Microsoft 的模式说明](https://learn.microsoft.com/en-us/azure/architecture/databases/guide/transactional-out-box-cosmos)；不要求采用文中的 Cosmos DB 或 Service Bus。

### A05：检查消息记录等派生数据的权限

这是本轮结合源码发现的新增重点。

`Service/Email/EmailPushService.Submission.cs` 中，当前邮件管理员查询记录可不限制发送人／应用，并返回邮件主题；微信队列记录按来源所有者返回内容。接入任务通知以后，这些现有规则不能自动等同于任务内容授权。

因此需要额外设计：

- 工作任务消息的来源、业务对象及收件人关联不可由外部随意声明。
- 通道运维权限默认只查看必要的发送状态、错误类别和脱敏路由信息；任务标题、正文、附件和摘要另按任务权限控制。
- 通用消息记录、重试、导出、日志、Agent／MCP 查询，都要检查受保护的任务来源。
- 重试前重新检查收件人与内容范围；原发送者停用不应迫使系统伪造其有效登录身份，可信业务作业按自身来源验证处理。
- 已外发消息无法依赖系统撤权收回，外部内容采取最小必要原则，详细材料通过受控链接访问。

目前尚未接入新任务通知，以上是应在接入前消除的设计风险，不表示已发生了工作任务数据泄露。

### A06：日终快照需要真实的一致性方案

原稿提出统一截止时间，但仅按实时表逐人查询，再给结果写上同一个时间，不能保证大家看到同一时刻的状态。

建议明确：

- 用受控的一致性读取形成基础快照，再按收件人、视角和权限生成摘要；或用完备的版本历史重建指定截止状态。
- 原始业务快照与实际发出的内容版本分别记录，发送前撤权时可裁剪／取消并留痕。
- 普通补发引用原快照；如果重新计算，生成新版本，不能悄悄替换原日报。
- 明确补发窗口、工作日历来源、时区、无任务时的处理和一个人多角色时的合并方式。

具体 SQL 一致性实现需结合现有数据库设置验证，不在本次评审中直接开启数据库级选项。

### A07：并发控制区分结构变更与追加记录

原稿的版本与幂等方向保留，但不宜所有写入都竞争同一个任务版本。

- 下派、要求修改、转派、取消及提交等状态变化检查任务相关版本。
- 排期、成果草稿各有自己的版本，避免互不相关的编辑相互覆盖。
- 进展和讨论采用追加记录及幂等标识；必要时校验当前办理权和所依据版本，但不因每条评论而使所有人打开的表单失效。
- 回执查询仍要重新授权，不能因为某人知道旧请求编号，就返回其现已无权查看的任务内容。

### A08：MCP 接入先验证，再确定技术范围

先选实际客户端，验证“连接 → 本人查询 → 文字汇报 → 文件上传 → 正式提交 → 网页查看结果”的完整链路。

- 支持自定义认证头的客户端可采用个人密钥兼容方式；这不能直接标为完整 OAuth 实现。
- 需要标准远程用户授权的客户端，单独实现或接入授权服务，校验资源和用户授权；具体参考 [MCP 2025-11-25 授权规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)，该引用不代表宣称它是当前最新协议版本。
- 新入口与匿名工具集必须隔离，同时验证新任务内容不会经通用消息记录／附件等旁路返回。
- 除密钥到期／撤销外，增加本人查看凭证使用历史、按用户／凭证限流、分页和结果大小上限。
- 对正式提交，确定业务需要“授予客户端代办能力”还是“每次有可验证的真人确认”。严格确认使用一次性、绑定版本和材料的确认机制；需要额外页面时明确告知体验成本。

协议工具提示不替代业务权限；关于工具调用展示和人工参与，参考 [MCP 工具交互说明](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。

### A09：区分上传、可用、预览与提供给 AI 的权限

建议文件状态至少能表达上传中、校验中、可用、拒绝。完成传输不等于文件已可正式提交。

- 一期明确允许格式、单文件／单任务／个人配额、预览范围和保留期限。
- 按能力接入恶意文件检查；未验证的文件不交给自动预览／解析流程，不宣称仅凭扩展名就完成安全检查。
- 多实例共用持久存储，临时文件回收与正式成果保留分开，数据库记录和实际文件都纳入备份及恢复验证。
- 员工有网页查看权限，不意味着默认将所有附件字节交给外部 AI 客户端；元数据读取、内容下载／提供给模型可分别授权。
- 任务正文与附件中的自然语言只作为业务数据，不应让其改变系统权限或指挥服务端执行任意操作。

文件隔离存储、类型／内容验证与配额策略参考 [OWASP 文件上传建议](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。

### A10：增加上线后的可观测性和恢复验收

除了原稿用例，还应验证：

- 任务命令、MCP 请求、上传、通知、通道结果能通过关联编号追踪，日志不记录完整密钥和无必要的成果正文。
- 监测待处理作业积压、最老等待时长、日终是否按计划生成、通知失败／待核实、文件容量与异常授权拒绝。
- 定义故障处理负责人、告警通道和重试／人工核实方式；不能靠员工投诉才发现整天没发日报。
- 在数据库迁移、旧新实例同时运行、回滚及文件恢复后验证业务仍可办理。
- 作业超时接管后，旧实例不能覆盖新实例的处理结果；状态更新检查租约所有者和当前状态。

这些是本模块交付内容，不要求为一期单独购买完整运维平台。

## 4. 对原稿的直接修改建议

| 原稿位置 | 建议调整 |
|---|---|
| 第 1／3 节：功能与页面 | 增加交付标准、任务问答、站内待办、手机办理和草稿恢复；顶层页面聚合；人员负荷改为有依据的数量／等待指标 |
| 第 4 节：流程 | 明确责任待办人、要求版本、原承诺／新承诺／预测、退回与重开规则，避免状态膨胀 |
| 第 5 节：权限 | 补充交接、代理有效期，以及业务数据经消息记录／日志／外部客户端流转后的权限 |
| 第 6 节：表结构 | 补足要求版本和附件关联；拆清业务事件／投递；允许据约束调整表数量 |
| 第 7／8 节：接口与 MCP | 按资源划分版本；补充评论／关联后续任务契约、凭证使用记录、限流、正式确认机制与真实客户端验收 |
| 第 9 节：日终与消息 | 增加自动生成、数据不足标记、空摘要／催办策略、一致性快照、通道记录权限与摘要版本 |
| 第 12 节：实施顺序 | 客户端验证前置，尽早跑通包含 MCP、文件和日终的最小完整业务链 |
| 第 13 节：验收 | 增加原承诺统计、未更新语义、交接代理、消息记录旁路、回执撤权、快照一致性、备份恢复和作业告警 |

## 5. 建议优先级与实施方式

| 优先级 | 内容 |
|---|---|
| 开发前定稿 | 应用／工作空间归属；主责与交付标准；完成／验收规则；排期批准；日终收件人、日历与时段；目标客户端与正式确认方式 |
| 首次上线应具备 | 独立权限与交接路径；版本和幂等；网页与 MCP 核心办理；文字／图片／文件；站内待办；可靠日终；来源隔离；基本监测和备份恢复 |
| 可后续扩展 | 批量派发模板、复杂依赖／多层子任务、完整容量规划、原生 App、离线、绩效评分、复杂组织同步和可视化流程设计器 |

建议将原稿“先全部网页、再通知、最后 MCP”调整为：

1. 先定关键业务规则，并验证一个真实 MCP 客户端的认证、确认和文件能力。
2. 用两种业务身份跑通一条最小完整任务：下派、评估、节点、网页／MCP 汇报、成果、按选定规则完成、两种日终摘要。
3. 完善多人授权、交接、并发、异常恢复和通道权限，再进行小范围真实试点。
4. 根据试点补充批量效率、管理视图和统计，不把尚未验证的管理指标提前当成绩效依据。

“最小完整任务”必须覆盖用户已经明确提出的核心能力，不能以简化为由取消个人 MCP、文件／图片或分角色日终同步。

## 6. 产品评审应作出的决定

保留原稿 D1—D6，再补充以下判断，并记录选择及影响：

- 交付标准由谁填写，文字／图片／文件哪些情况下必需。
- 简单任务是否只需一个承诺时间，多节点是否按需启用。
- 员工按时提交但领导晚验收如何统计；延期是否同时保留首次承诺与最新批准口径。
- 没有更新如何呈现，是否需要员工确认日终摘要，空摘要是否发送。
- 领导／员工离岗时谁负责交接，代理范围与期限如何确定。
- 哪些内容允许发送给外部 MCP 客户端，正式动作采用客户端代办授权还是每次真人确认。
