# 独立工作任务与个人 MCP：改造设计评审稿

日期：2026-10-26。状态：待业务评审，未实施。

本文依据当前前后端源码整理，说明建议新增和修改的内容。本文不是已完成功能清单，也不是测试报告；本次没有修改业务代码、执行数据库迁移、创建个人密钥或发送通知。

## 1. 评审结论

建议在现有系统中新增独立的“工作任务”模块，采用现有 Vue 3 前端、.NET 8 后端和 SQL Server，不另建账号系统，不要求拆成微服务。

整体关系：

```text
网页办理 ───────────────┐
个人认证的 MCP ─────────┼→ 工作任务业务服务 → 独立任务表、权限、附件、操作记录
受控文件上传入口 ───────┘          ↓ 同一事务记录待通知事件
                            后台处理 → 现有微信／邮件发送队列
```

工作任务与原项目任务分别管理。原项目任务、项目文件、项目负责人不作为新模块的业务归属或授权依据。

### 1.1 已明确需求与建议项

| 性质 | 内容 |
|---|---|
| 已明确 | 编辑工作任务，下派给指定人员；员工评估并回复时间节点；汇报进展；使用文字、文件或图片说明成果 |
| 已明确 | 每天下班前，向领导和员工分别同步不同的任务状态 |
| 已明确 | 工作任务独立于项目；重新划分业务角色与权限 |
| 已明确 | 员工使用自己的 MCP 访问密钥获取自己的任务并汇报、上传材料 |
| 设计建议 | 一条任务一名主责人；多人分别交付时生成多条任务，可共用批次号 |
| 设计建议，待确认 | 是否必须由领导验收后才算完成；超期排期和延期是否必须审批 |
| 待确认 | 员工日终同步发给全部有相关任务的员工，还是仅当天提交／完成任务的员工 |
| 待确认 | A/B 应用的数据关系、管理范围、日终时间与工作日、通知通道、实际 MCP 客户端 |

本文按“独立模块、权限默认收紧、保留完整记录”设计；待确认项不能当作用户已同意的业务规则。

后端路径均相对于 `project-management-backend-system/`，前端路径均相对于 `project-management-system/`。

## 3. 建议交付的页面与功能

| 页面／入口 | 新增内容 | 主要使用者 |
|---|---|---|
| 我的工作 | 待评估、进行中、待补充、待验收、已完成；查看节点、逾期和阻塞 | 员工 |
| 工作下派 | 草稿、编辑、选主责人、要求时间／交付说明、正式下派、转派与取消；批量派发后分别跟踪 | 主管 |
| 任务详情 | 要求、评估、排期版本、节点、进展、成果、附件、操作时间线；按权限展示操作按钮 | 获准参与者 |
| 成果处理 | 提交说明、上传文件／图片、预览本次成果；按选定规则完成或进入验收 | 员工 |
| 待我验收（如启用） | 查看指定给自己的提交版本，通过／退回并填写意见 | 指定验收人 |
| 团队工作 | 授权范围的任务列表、人员负荷、待评估、逾期、阻塞、待验收和催办 | 主管、督办 |
| 工作任务设置 | 工作组、成员／负责人、业务角色及范围、流程与通知规则、失败通知记录 | 获准管理员 |
| 个人 MCP 连接 | 创建凭证、选择允许操作和到期时间、查看最近使用、撤销／轮换、连接说明 | 本人 |

复用同一套详情和表单组件，避免“我的任务”和“团队任务”各写一套业务逻辑。后端返回本条任务的 `allowedActions` 帮助界面显示；真正的权限仍在每次服务端请求中判断。

人员选择器只能搜索当前操作者可下派的人员。文件展示可复用界面组件，但调用新模块的上传、预览和下载接口。

一期采用单主责制。协作人可按授权补充进展和材料，关注人只读；多人各自承担同一要求时，分别生成任务，避免其中一人提交就替所有人完成。

## 4. 任务流程及修改规则

### 4.1 建议流程

```text
草稿 → 已下派／待评估 → 执行中 → 已提交／待验收 → 已完成
                         ↑             │
                         └── 验收退回 ──┘

若业务选择免验收：执行中 → 正式提交 → 已完成
正式任务可按权限取消；草稿可删除。
```

以上“验收”分支是建议，需评审确认。是否需要验收应记录为任务的流程规则快照，避免以后修改全局设置导致历史任务突然改变流程。

| 环节 | 处理规则 |
|---|---|
| 编辑下派 | 保存草稿不通知；正式下派才通知员工。记录创建人、下派人、主责人、汇总负责人；启用验收时记录验收人 |
| 时间要求 | 区分领导要求时间和员工承诺时间。没有固定期限时明确选择“由员工评估排期”，不自动填虚构日期 |
| 员工评估 | 回复能否承担、预计开始、预计完成、具体节点、风险／协调事项。“无法承担／需协调”留在待处理环节，由主管协调或转派 |
| 排期确认 | 建议满足要求的排期直接生效；超出要求或申请延期时进入待确认。保留原承诺，批准前不覆盖生效版本。此规则需确认 |
| 进展汇报 | 记录进度、说明、阻塞、下一步及附件；百分比与流程状态分开，填 100% 不直接算正式完成 |
| 正式提交 | 先保存草稿，提交时固定文字、附件和节点版本。至少应有有效文字说明或成果材料；是否必须有附件按任务要求配置 |
| 验收 | 仅指定且有能力的验收人可通过或退回；退回保留旧提交、原因和材料，新提交生成新版本 |
| 修改要求 | 已下派后的要求／时间变更生成版本并通知相关人；关键变化需要员工重新确认，不能悄悄覆盖原要求 |
| 转派 | 检查新主责人范围与承接状态；保留历史责任链。旧员工停止办理，历史材料查看权按显式授权处理 |
| 取消 | 记录原因并通知，保留历史。已完成任务不通过普通修改接口退回进行中 |

逾期、阻塞、等待排期批准是独立标记／子状态，不能替代任务主状态。区分执行逾期、评估逾期和验收逾期，避免员工已提交却继续计入员工未交付。

## 5. 权限怎么改

### 5.1 不重置原系统角色，新增模块业务角色

建议新增模块内部角色代码，例如 `worker`、`dispatcher`、`supervisor`、`work-admin`。这是一组新业务定义，不直接将所有现有“管理员／工程师／普通用户”映射进来。

| 角色 | 默认允许 | 默认限制 |
|---|---|---|
| 执行员工 | 办理本人主责任务；按单条任务授权协作 | 不能查询所有员工任务、替他人承诺或验收自己成果 |
| 派发主管 | 在授权人员／工作组内下派、协调排期、跟进；被指定且有验收能力时验收 | 主管身份不能直接查看／处理所有任务 |
| 督办人员 | 查看授权范围、催办和管理汇总 | 默认不能修改员工汇报或批准成果 |
| 工作任务管理员 | 管理获准范围的组织、业务授权、流程和通知配置 | 不自动获得所有正文、附件、代办与验收权限 |
| 平台管理员（已有） | 继续管理账号、应用准入与技术配置 | 不用 `*` 或 `AllResources` 绕过工作任务的关系和流程约束 |

建议首次启用时，由平台管理员明确指定首位工作任务管理员及其可委派范围，记录审计；这项配置能力不附带任务内容读取权。后续管理员不能授出超过自身可委派边界的权限。

### 5.2 每次授权绑定范围

有效权限同时满足：

```text
账号有效 + 应用准入 + 模块功能能力
    + 某一份“业务角色—适用范围”授权
    + 当前任务身份／可见关系 + 当前流程条件
MCP 再增加：本人凭证有效 + 凭证允许操作 + 本人相关任务限制
```

不能把角色集合和范围集合分别求并集后再组合。例如，某人是“维修组主管”和“生产组员工”，不能因此取得生产组派发权。

建议范围类型：本人相关、直属成员、本组、含下级组、指定组、指定人员、显式全模块。组织层级有环、成员重复、组负责人停用等情况需要校验。跨组派发必须显式授权。

列表、详情、计数、人员选择、导出、附件预览下载、汇总和 MCP 工具使用同一套范围判断。仅隐藏菜单、仅在查询结果返回前过滤，均不足以作为授权。

账号停用、授权撤销、成员调组、任务转派后，后续操作按当前有效授权校验。即使已有链接、任务 ID、旧令牌或上传票据，也不能继续越权办理。

## 6. 数据库新增内容

建议新增独立表前缀 `work_`，以下是供评审的逻辑表划分，共 18 张；不是本次已经建立的表。验收表仅在启用验收时使用。

| 建议表名 | 用途与核心字段 |
|---|---|
| `work_group` | 工作组／部门：应用、名称、上级组、负责人、启停 |
| `work_group_member` | 组成员、主要汇报人、有效期；保留调整记录 |
| `work_role_grant` | 用户、模块角色、范围类型／范围目标、是否含下级、有效期、授权人、可委派边界 |
| `work_task` | 编号、标题、要求、优先级、创建／下派／主责／验收／汇总负责人、归属组、要求时间、状态、生效排期、流程快照、版本 |
| `work_task_participant` | 协作／关注关系、单任务读写能力、有效期 |
| `work_task_plan` | 员工评估、可行性、协调说明、预计开始／完成、版本、待确认／生效／拒绝及批准信息 |
| `work_task_milestone` | 所属排期版本、节点要求、承诺时间、交付说明；旧版本不覆盖 |
| `work_task_report` | 进展／阻塞／下一步、关联节点、说明、提交人和来源、时间 |
| `work_task_submission` | 成果草稿及正式提交版本、说明、提交人、提交时间、固定的附件集合／内容摘要 |
| `work_task_attachment` | 文件键、原文件名、实际类型、大小、校验和、上传人、任务、关联对象及状态；不以原文件名作为存储键 |
| `work_task_upload_session` | 上传会话、票据摘要、任务／草稿／本人绑定、允许大小类型、有效期、完成状态 |
| `work_task_review` | 对某个提交版本的通过／退回、意见、验收人和时间 |
| `work_task_audit` | 操作人、任务、动作、来源、关联版本、变更摘要、请求编号、结果 |
| `work_personal_key` | 所有人、应用、密钥摘要、允许操作、到期、撤销／轮换、客户端标签、最近使用；不保存可直接返回的明文 |
| `work_command_receipt` | 写操作幂等键、参数摘要、操作类型、办理人、业务结果编号、保留期限 |
| `work_task_outbox` | 待处理业务事件及派生通知作业：父事件、收件人、视角、通道、幂等标识、状态、租约、重试时间、通道记录引用 |
| `work_task_digest` | 日终摘要：业务日、统一截止时间、收件人、员工／领导视角、时间段、内容快照、生成版本 |
| `work_notification_rule` | 日终时间、时区、工作日／例外日期、接收人规则、通道、模板版本、失败／补发策略 |

### 6.1 关键约束

- 身份字段统一引用现有 `UserId` 字符串，最长 64；不能沿用部分旧项目接口的数字用户 ID。
- 业务 ID 可用 SQL Server `bigint`，对前端／MCP 统一序列化为字符串，避免 JavaScript 大整数精度丢失。
- 暂按 A/B 隔离设计：主记录具有 `AppCode`，子记录通过父记录校验归属；凭证同样绑定应用。若评审选择共享，需要先确定共同工作区模型，再落表，不能只取消应用过滤。
- 任务编号在应用内唯一；组成员与有效参与关系防重复；角色授权保持角色与范围成对。
- 列表索引优先覆盖“应用＋主责人／归属组＋状态＋承诺时间”，历史表覆盖“任务＋版本／时间”。
- `work_command_receipt` 唯一键包含应用、办理人、操作类别和幂等键；同键不同参数拒绝，重复相同请求返回原结果。
- 日终摘要唯一键建议为“应用＋业务日＋收件人＋视角＋计划时段”；派生投递作业按“来源事件／摘要＋收件人＋视角＋通道”去重。
- 写入任务变化、版本、审计、幂等结果和待处理事件应在同一数据库事务内完成；网络发送放在事务外。
- 已提交成果和验收记录不原地改写；修改产生新版本。附件删除／保留策略不能破坏已提交版本的证据链。
- 新增日期采用 UTC 存储，接口输出带时区的 ISO 时间，界面按配置时区显示；业务日按日终规则时区计算。
- 未评估、未提交、未验收、未发送的时间保持 NULL。遵循后端 `AGENTS.md`，每个可空 SQL 字段显式声明 `IsNullable = true`，不填假日期。
- 迁移可重复执行；验证新库初始化、旧库增量迁移、已有数据保留及真实插入。多实例发布时由一个受控迁移过程执行，其他实例等待版本就绪。

## 7. 后端接口新增内容

以下路径是建议契约。网页接口要求有效登录及当前应用上下文；个人密钥只被专用 MCP／上传入口接受，不因此获得普通后台管理 API 的访问权。

| 接口组 | 建议接口 | 用途 |
|---|---|---|
| 我的／团队任务 | `GET /api/work-tasks`、`GET /api/work-tasks/{id}` | 分页、状态、节点、详情；服务端确定可见范围 |
| 可选人员 | `GET /api/work-tasks/assignable-users` | 只返回可下派的人员，不使用全员邮件收件人接口代替 |
| 草稿 | `POST /api/work-tasks`、`PATCH /api/work-tasks/{id}/draft`、`DELETE /api/work-tasks/{id}/draft` | 创建、修改和删除未下派草稿 |
| 正式任务命令 | `POST /api/work-tasks/{id}/dispatch`、`/revise`、`/reassign`、`/cancel` | 明确的状态操作；记录原因、版本和通知事件 |
| 评估与排期 | `POST /api/work-tasks/{id}/assessments`、`/plans/{planId}/approve`、`/plans/{planId}/reject` | 评估、确认、拒绝；延期采用新排期版本 |
| 进展 | `POST /api/work-tasks/{id}/reports` | 文字、进度、阻塞、节点和已授权附件 |
| 成果 | `POST /api/work-tasks/{id}/submissions`、`PATCH /api/work-tasks/{id}/submissions/{submissionId}`、`POST /api/work-tasks/{id}/submissions/{submissionId}/submit` | 成果草稿与正式提交分开；正式版本不可再编辑 |
| 验收（如启用） | `POST /api/work-tasks/{id}/submissions/{submissionId}/reviews` | 对固定成果版本通过／退回 |
| 附件 | `POST /api/work-task-uploads`、`PUT /api/work-task-uploads/{uploadId}/content`、`POST /api/work-task-uploads/{uploadId}/complete` | 申请、受控上传、验证完成；各接口使用专属授权策略 |
| 预览／下载 | `GET /api/work-task-attachments/{attachmentId}`、`/{attachmentId}/content` | 文件信息与受权内容访问，不提供永久公共目录 |
| 业务组织与授权 | `/api/work-task-admin/groups`、`/members`、`/role-grants` | 工作组、成员和角色—范围配置；每个管理动作检查可委派边界 |
| 规则与记录 | `/api/work-task-admin/notification-rules`、`/notification-records`、`/digests` | 配置、查看有权限的结果、受控补发；不允许随意替换收件人 |
| 个人凭证 | `GET/POST /api/work-task-keys`、`POST /api/work-task-keys/{keyId}/revoke`、`/rotate` | 登录后仅管理本人凭证；创建／轮换仅一次展示明文 |
| 写入回执 | `GET /api/work-task-operations/{requestId}` | 断线重试后确认自己的操作结果 |

新增统一 `WorkTaskActorContext` 和领域授权服务。身份从已验证的登录会话／个人凭证产生；请求中的人员字段只用于合法业务目标，不能指定操作者身份。

正式写操作带 `expectedVersion` 和幂等标识。过期版本返回明确的冲突提示，让用户刷新后处理；参数缺失、无权、状态不允许、凭证失效分别返回可理解的错误，不能全部包装成“服务器内部错误”。

新模块统一响应外壳和 camelCase 字段，日期明确包含时区；在模块输出层适配，不全局修改旧接口的 JSON 设置，以免影响现有看板。

## 8. 个人 MCP 如何接入

### 8.1 必须新增的隔离层

建议新增 `/mcp/work-tasks`，使用独立认证策略、个人调用上下文和工具白名单。

当前 `Program.cs` 注册一套 MCP 处理器。不能只新增一个 `MapMcp` 地址，仍复用匿名处理器及全量工具注册表。需要按服务端确定的端点策略分离工具发现与执行；旧端点拒绝新工具名，专用端点也只允许工作任务工具。

实现前验证当前 MCP SDK 在本项目中的端点分流方式。可共享协议适配代码，但工具清单、认证策略、调用上下文必须隔离；不能信任请求参数声称自己来自哪个入口。

个人凭证属于本系统，不是模型平台 API Key。建议随机高熵密钥、仅创建时显示、数据库保存摘要，通过 HTTPS 认证头传递。每次调用检查凭证、账号、应用授权、模块角色、任务身份和状态。

现有机器客户端令牌和网页令牌不能自动在此入口等价通行；若将来支持 OAuth，令牌应明确绑定此资源与用户授权。MCP 后台调用不延长网页的 20 分钟无操作会话。

### 8.2 建议开放的员工工具

| 工具示例 | 允许做什么 | 共用服务 |
|---|---|---|
| `worktask.my.list`、`worktask.my.get` | 查询本人相关且可见的任务 | 任务查询与授权 |
| `worktask.assessment.reply` | 回复评估和节点；超出要求按排期规则处理 | 评估／排期命令 |
| `worktask.progress.report` | 记录文字、进展、阻塞及获准材料 | 进展命令 |
| `worktask.deliverable.draft` | 创建／更新本人任务的成果草稿 | 成果草稿服务 |
| `worktask.attachment.begin`、`worktask.attachment.complete` | 申请上传、验证材料并取得附件 ID | 上传会话服务 |
| `worktask.deliverable.submit` | 正式提交已确认的成果版本 | 成果提交命令 |
| `worktask.report.status` | 查询自己的写入结果与当前处理状态 | 幂等回执查询 |

即使用户同时是主管，此个人入口也只提供员工侧本人办理；不默认开放团队查询、替人下派、验收、组织授权和强制完成。查询／进展／排期／成果／附件分别配置凭证能力，最终能力不能超过账号现有业务权限。

正式承诺和成果提交建议先展示结构化预览，再让员工确认。若要求证明真人批准，需要可信客户端确认机制或系统确认页面，并绑定具体任务、版本、内容和附件；模型自行填 `confirm:true` 不构成可信批准证明。

### 8.3 文件与客户端兼容

推荐主流程：MCP 申请上传会话 → 支持上传的客户端通过 HTTPS 发送文件 → 服务端验证完成 → MCP 引用附件 ID 汇报／提交。

- 上传票据绑定本人、应用、任务、草稿、文件约束和短有效期；校验实际字节、大小、类型、校验和及任务当前权限。
- 票据只授予该次上传；不能用于读取任务、下载材料或调用其他工具。对票据及认证信息做日志脱敏。
- 客户端不能直接上传文件时，返回受控网页上传入口；网页登录或专用短期授权后选择文件，再继续引用附件。
- 小文件 Base64 可作为经过限额验证的补充工具，不作为大附件主通道；不能承诺所有 MCP 客户端都能读取本地文件并上传。
- 只传 `C:\...\照片.jpg` 不等于完成上传。普通外链也不等于已经归档的成果附件。
- 文件用独立持久化目录或对象存储，置于发布包之外；多台后端共用持久存储。使用唯一文件键，同名文件不覆盖旧成果。
- 预览／下载重新授权；控制临时文件清理、总容量和保留期限，正式成果不由临时清理任务删除。

先确认目标客户端是否支持远程 MCP、自定义认证头和所需文件交互。支持自定义认证头时可先提供个人密钥接入；如果目标客户端必须使用 OAuth，则将用户授权流程、发现、PKCE、资源校验等作为单独工作包。现有机器 `client_credentials` 不能直接替代员工授权。

## 9. 日终汇总与消息推送怎么改

### 9.1 同一数据，不同视角

| 视角 | 建议内容 |
|---|---|
| 员工 | 本人今日进展／提交／完成、待评估、明日节点、逾期、阻塞、被退回及下一步 |
| 领导 | 授权范围内新增／提交／验收完成、待评估／待验收、逾期与阻塞、人员分布、需领导协调事项 |

严格区分“员工已提交”和“已验收完成”，不把通道发送成功当作员工已读或已接受任务。

日终内容按同一截止时刻生成快照；每个收件人的可见任务仍独立计算。一个人既是员工又是主管时，按视角分别生成或分段展示，不能因此扩大数据范围。

员工接收范围仍需评审：建议默认覆盖“有进行中／待办任务或当天有变更的员工”，但用户原话也可能仅指当天完成任务的人，不能在实现中自行定死。

### 9.2 在现有通知基础上新增的内容

1. 任务命令在事务内记录业务事件，通知失败不回滚已完成的业务办理。
2. 后台按事件生成个人待办提醒；按配置时区、工作日及日终时段生成角色摘要。立即通知哪些事件可在规则中配置。
3. 建立专用内部 `IWorkTaskNotificationService`，依据已落库事件解析收件人和模板；不开放任意发送人／收件人／正文的匿名业务入口。
4. 扩展邮件／微信队列，识别可信工作任务事件来源；入队及真正发送前校验业务来源、收件人当前权限和通道授权。不伪造用户发送权限，也不借用“外部 MCP”标识绕过检查。
5. 复用现有通道限流、发送记录和不确定状态处理。日终摘要与通道记录关联，页面显示待处理、失败、已发送、结果待核实。
6. 事件、摘要和派生投递都有唯一标识；多实例通过 SQL 租约争抢工作。正常重试去重；通道结果不确定时标记待核实，避免自动重复发送。
7. 重启后补处理持久化的未完成作业；跨过日终时间的补发窗口和超过窗口后的处理规则必须可配置。
8. 发送前权限发生变化时，重新裁剪／生成该收件人的内容或取消投递，记录摘要版本；不能把旧快照中的敏感内容发给已失去权限的人。

一期建议沿用现有 `BackgroundService + SQL Server` 技术体系，新增独立任务作业处理器，不新增 Redis、消息中间件或调度产品作为前置条件。以后若需要集中作业控制台，可以单独评估调度平台；持久化、去重、租约和失败处理仍必须具备。

微信复用当前项目的 ClawBot 通道，不等同于已经接入企业微信或钉钉。邮件发送摘要和受控详情链接，不能把当前通道描述为已经支持成果附件随信发送。

## 12. 实施顺序与上线方式

| 阶段 | 实施内容 | 阶段结束可评审结果 |
|---|---|---|
| 0：规则定稿 | 确认第 14 节决策；验证目标 MCP 客户端和当前 SDK 的端点隔离方式 | 固定状态、权限、数据归属及接入契约，防止建表后再反复改身份模型 |
| 1：完整网页闭环 | 组织与配对授权、编辑下派、评估排期、进展、文字／文件／图片成果、按规则完成／验收、审计 | 可由主管和员工完成一条真实业务链；不依赖 MCP 才能用 |
| 2：状态同步 | 业务事件、角色摘要、可信通道适配、发送结果、日终租约／恢复／补发 | 到指定时段分别收到正确范围与不同视角的状态 |
| 3：个人 MCP | 凭证生命周期、本人查询／评估／进展／成果、上传会话与兼容入口、回执 | 网页与 MCP 交叉操作一致，已撤销／越权调用被拒绝 |
| 4：试点上线 | 指定工作组、小范围账号开通，验证实际通道、存储与客户端 | 业务规则、通知口径与记录得到确认后再扩大范围 |

这是实施顺序，不表示个人 MCP 或文件上传可以从最终需求中省略。MCP 可先验证文字链路，再完成实际客户端的文件闭环后统一验收。

建议功能开关分开控制网页入口、MCP、事件通知和日终作业。数据库采用新增表及兼容字段，不删除或迁移旧项目数据。A/B 菜单按确定的应用范围启用。

多实例部署需要共同数据库、共同文件存储、任务租约和一致密钥验证配置；文件不能只放某个实例的发布目录。迁移先行，数据库版本就绪再放开功能。回滚时关闭入口和作业开关，保留任务／附件／审计及队列数据；不以删表作为应用回滚办法。

现阶段不新增人员排班、绩效考核、工时计费、复杂 BPMN 流程设计器和自动 AI 验收；这些若后续需要，另行评审。

| WT-08 | 旧 `/mcp`、`/mcp/v2`、外部 HTTP 工具入口枚举／强行调用任务工具 | 看不到并且执行不了新任务工具，单独保护新地址不能代替此验证 |
| WT-09 | 用机器令牌／错误应用令牌；撤销密钥、停用账号、移出授权、转派后继续调用 | 身份类型和资源不匹配被拒；权限变化及时生效；不续期网页空闲会话 |
| WT-10 | 目标客户端实际连接、文字汇报、图片／文件上传、断线查回执 | 形成真实客户端闭环，不用模拟成功代替文件接入验证 |
| WT-11 | 日终两种视角、一个人多角色、无当日变更、休息日、跨截止时刻 | 按确认口径生成，不串范围、不混淆提交与完成 |
| WT-12 | 两个后端实例、作业重启、发送中断、通道未绑定、发前撤权 | 正常不重复入队；不确定结果待核实；失败可查；不向失权用户发旧敏感摘要 |
| WT-13 | 空库、已有数据的旧库、重复初始化、nullable 字段真实插入 | 结构和约束正确，原项目／账号／菜单数据不被覆盖 |
| WT-14 | 原项目任务、既有看板／A/B 入口、原匿名工具集、手工消息队列 | 与本次改造接触的兼容路径正常，新旧业务没有串表或串权限 |

## 14. 本次请重点评审的业务决定

| 决策 | 建议方案 | 需要确定的内容 |
|---|---|---|
| D1 应用归属 | 先在指定一个应用启用，按应用隔离，另一应用后续显式开通 | 本次放 A 还是 B；两边是否需要共同任务数据。该项在迁移前确定 |
| D2 责任与管理 | 一条任务一个主责人；工作组＋显式角色范围；跨组单独授权 | 是否需要多人独立交付；直属／下级范围、转派和首位任务管理员 |
| D3 完成标准 | 建议正式提交后由指定领导验收；可选择免验收模式 | 上传并提交是否就算完成；退回、自验收限制、附件是否必需 |
| D4 排期变更 | 建议满足要求自动生效，超期／延期由下派负责人确认 | 是否需要每次排期都审批；要求变更是否重新评估 |
| D5 日终同步 | 建议按工作日、统一截止时间；领导看授权团队，员工看本人待办／当日变化 | 员工是否仅限当天完成任务者；具体时间、工作日、微信／邮件／两者及补发窗口 |
| D6 开放接入 | 个人入口只做本人办理；每个客户端单独凭证；按客户端能力选个人密钥或 OAuth | 实际客户端及部署可达性、文件能力；正式提交是否要求可证明的真人确认 |

建议评审通过后先确定这些规则，再开展数据库和接口实现。本稿只做变更设计，没有预先替业务选择未确认项。
