# 小时产量与目标看板 v1.0

## 本次业务与入口

新增独立小时产量模块，不替换原生产监控、设备卡片或产线工艺看板。首期不使用 Redis，不引入通用任务调度平台。

- 管理入口：产线看板 → 小时产量看板、小时产量配置。
- 权限键：`HourlyProduction`（查看）、`HourlyProductionConfig`（配置）。
- A 系统默认组件路径：`/production-dashboard/hourly-production`、`/production-dashboard/hourly-production-config`。
- B 使用自己的动态菜单记录；已有产线目录时只补缺失子菜单，不覆盖原菜单、不批量授权普通用户。没有目录时由管理员从业务组件目录加入。
- 看板数据按 AppCode 隔离，并校验线体、数据源范围。管理员沿用现有平台权限机制。
- 公开大屏：`/#/public/hourly-production/<看板编码>`，必须先保存并启用“公开免登录查看”。
- 公开页面仅返回显示所需的汇总，不返回原始 SN、数据源绑定、收件人或配置；没有设置、编辑和保存按钮。所有后台写接口仍须登录授权。

默认两条线，每条生成气密、抽真空、注氟、安规仪、商检、上压缩机、电控。名称可改，工序可新增、移除、排序和停用。同一“对齐行编码”的工序横向对齐；不是依靠中文名称自动匹配。

线体累计仅取指定的汇总工序，默认商检，不能把所有工序产出相加。线体小时目标默认沿用汇总工序目标，也可以开启独立线体目标。

大屏保留浅色工业风格；配置页使用系统主题变量。图表高度根据视口和工序数适配，过多工序保留滚动，不无限缩小字体。页面一次请求两条线数据；图表本身不各自轮询。

## 数据链路与接入约定

```text
HTTP实时报文 → 校验 → 过站接收暂存 → 最新快照更新或旧时间忽略
中转WebSocket → 既有中心消息队列 → 持久化水位投影 → 过站接收暂存
过站暂存 → 去重/条件/返工 → 过站台账 + 小时汇总
小时汇总 → 大屏 / AI / 冻结报表 / MCP / 推送队列
```

HTTP接收使用本次实际 `Data` 或 `DataList` 的每一帧，不能使用合并后的最后字段值。旧时间报文也会先保存生产事件，仍保留原来的“旧报文不得覆盖最新快照”行为。

只有包含当前规则触发字段、并匹配条件的帧才进入HTTP过站暂存；仅更新温度等无关字段的遥测增量不会占用统计队列，也不额外要求事件编号。

配置参与统计的实时上报应提供稳定且唯一的 `messageId`；同一次重传必须沿用原编号。没有编号时拒绝参与该配置源的统计上报，避免条件计数/求和重复；未绑定小时统计的来源不额外要求编号。SN 与时间不足以在所有并发情况下替代可靠事件编号。

示例：

```json
{
  "tenantMark": "factory",
  "deviceMark": "airtight-01",
  "messageId": "station-pass-20261022-000001",
  "time": 1792627500000,
  "data": {
    "SN": "PRODUCT0001",
    "passTime": "2026-10-22T08:05:00+08:00",
    "line": "L1",
    "result": "OK",
    "rework": "0"
  }
}
```

数字时间戳示意值须由发送方按实际过站时间生成；绑定 `passTime` 时按该字段归属小时。

绑定说明：

- Realtime：SourceKey 为 tenantMark，DeviceKey 为 deviceMark，复用历史字段目录及共享中文映射。
- Edge：SourceKey 为 SourceId，DeviceKey 为边缘网关 DeviceCode，SourceDeviceCode 可进一步限定实际订阅设备。同一网关不是同一生产设备。
- 字段可使用目录中的 JSON Pointer，如 `/data/SN`、`/data/nested/value`，支持 `~1`、`~0` 转义及数组索引；也支持直接字段名、JSONPath。
- 时间字段留空使用报文发生时间；显式配置的时间字段缺失/格式错误会进入接收异常，不伪造时间。
- 条件字段按字符串精确匹配；例如绑定 `/data/line` 等于 `L1`，或绑定过站结果等于 `OK`。
- 不支持从最新快照还原过去漏传的所有 SN。新配置从后续接收开始统计，不自动导入此前所有历史队列。

## 统计口径

默认08:00—20:00。结束小于等于开始表示跨夜班；20:00—次日08:00归属开班当天的生产日。每段为左闭右开区间，支持末尾不足一小时的区间。

| 模式 | 行为 |
| --- | --- |
| DistinctSn | 按看板、线体、工序、生产日、SN 进行有效过站判定 |
| Count | 对本次满足过滤条件的事件计数，不靠SN变化猜测产出 |
| Sum | 对本次事件的数值字段求和，不是对累计仪表读数求和 |

求和事件值支持0至十亿、最多6位小数，数据库用 `decimal(28,6)` 保存，不以默认两位小数悄悄截断；超出约定精度进入接收异常。

默认返工规则：

1. 同一 messageId/帧/绑定只处理一次。
2. SN 首次有效过站计产出；明确标识为返工时按返工处理。
3. 后续相对上一次有效过站，小于等于30分钟忽略，不延长抑制窗口。
4. 超过30分钟且进入不同小时时段，计返工；“返工需跨小时”可关闭。
5. 明确返工字段可绕过“跨小时”要求，但仍遵守重复抑制，避免持续状态反复计数。
6. “返工同时计入产出”默认关闭，可配置。
7. 不同工序之间正常流转不属于重复返工。

08:50→09:10只有20分钟，不算返工。乱序到达时按发生时间重放同SN的判定，并以差量修正小时桶；不会把晚到事件强行算到接收小时。

未绑定显示未绑定；未来显示待开始；当前小时显示统计中，不做最终未达标判定。目标空或0都表示未设置目标，不除以0。完整小时产出大于等于目标显示绿色达标。

已有过站记录的看板不可直接改班次边界，已有记录的工序不可直接改统计口径/绑定。可新建编码，或复制看板后调整；移除工序不会删除已有台账，历史编码不可再次复用。名称、排序、启停、展示目标可调整。配置使用版本号防止覆盖其他人的修改。

唯一索引约束事件、桶、报表及发送批次；事务级数据库锁保护乱序重算及桶差量。后台持久化租约防止常规多实例重复调度；推送另由现有队列幂等约束保护。

已完成接收暂存保留7天；过站、小时结果和报表不套用边缘本地日库清理策略，首期不自动删除。其长期保留/归档策略应根据真实事件量另行配置，不暗中删除可重算依据。索引及短期汇总查询不替代容量与吞吐压测。

暂存清理按小时触发，每批最多1000条，积压时分批继续；不在每5秒统计循环中执行一次全量历史删除。

后台统计每5秒轮询，单轮中心投影200条、暂存统计100条；如现场吞吐超过处理能力需按压测调整批量/循环，不能承诺无限吞吐。存在未处理暂存或未追平中心批次时不冻结新报表，避免发送积压导致的假零产出。

## AI与小时推送

AI默认关闭，复用模型平台对 `production-dashboard` 的模型绑定。启动至少60秒后独立分析，只读取已汇总的统计；单次模型超时15秒，错误清空建议。模型请求不在读取接口、接收事务或统计循环中。

系统内推送为专用小时报表调度，不是通用对话任务平台：

- 每个完整小时结束后缓冲，默认2分钟。
- 重启只补配置窗口内且激活后结束的小时，默认2小时。
- 配置保存时间作为当前推送配置的激活边界，不追发修改前尚未生成的老小时。
- 线体可选，留空为两条线；按微信/邮件和收件人建立独立批次。
- 报表生成后冻结配置版本和数据快照；后续补传会修正实时统计，但不自动反复发送旧报表。
- 入队前重新验证真实发起用户、应用、看板和渠道权限；推送关闭或发起人权限被撤销时取消。
- 入队失败指数退避，最多10次；明确Failed可在记录页确认后重试。
- Queued仅表示进入既有微信/邮件队列，不等于送达。记录提供队列返回编号，到推送中心查询真实投递结果；Unknown不在本模块盲目重发。
- 物理发送继续遵守已有微信间隔/风控、邮箱服务配置及收件人有效性。
- 接收人从当前计划移除后，尚未入队的对应任务取消；超长微信报表分段入队，每段都有独立且稳定的幂等键。

初始 AI、公开发布和小时推送都关闭；部署不会自动联系真实用户。

## MCP V2工具

沿用当前标准 Streamable HTTP `/mcp/v2`，不用另起端口。服务名沿用已有前端配置的MCP名称；此次不更改认证模式。

| 工具 | 参数 | 返回 |
| --- | --- | --- |
| `hourly.boards` | `{}` | 已发布看板编码、名称、班次和线体名称 |
| `hourly.runtime` | `{"boardCode":"hourly_xxx"}` | 当前班次双线、工序小时统计及汇总 |
| `hourly.reports` | `{"boardCode":"hourly_xxx","current":1}` | 每页20份冻结报表 |

匿名直连或全资源授权客户端仅能读显式发布的小时看板，不开放配置写工具。内部网页登录仍按A/B及资源授权。

外部任务可定时读取 `hourly.reports`，再调用已有 `clawbot.send`、`email.send`，使用“报表编号+渠道+接收人”构成稳定幂等键，并遵守 `confirm:true`。读取不会标记已推送；本系统自动推送与外部任务应约定同一接收人的负责方，否则各自独立的业务批次仍可能重复通知。

调用示例：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "hourly.runtime",
    "arguments": { "boardCode": "hourly_xxx" }
  }
}
```
