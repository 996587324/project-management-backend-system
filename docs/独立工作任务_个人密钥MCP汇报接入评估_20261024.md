# 独立工作任务：个人密钥 MCP 汇报接入评估

日期：2026-10-24。

## 1. 结论

可以实现。建议将 MCP 作为独立工作任务模块的一个“本人自助办理入口”，与网页共用业务服务、状态机、角色和对象权限。

目标流程：员工使用绑定本人账号的凭证连接 → 查询自己的任务 → 回复评估/时间节点 → 汇报进展 → 上传文件或图片 → 确认提交成果 → 返回可追踪结果 → 纳入既有角色日报和即时通知。

这里的凭证是本系统签发的“工作任务个人访问凭证”，与外部模型服务的 API Key 分开。个人凭证不放入聊天正文或工具业务参数，由客户端连接配置携带。

当前独立工作任务与新业务角色仍处于评估阶段；本文是接入设计，不表示这些工具已可调用。本次未创建密钥、授权第三方、修改服务配置或发送汇报。

## 2. 当前 MCP 基础与必须补齐的差异

已具备：

- 官方 .NET MCP SDK 接入和 Streamable HTTP 服务基础。
- 工具注册、输入 Schema、业务调用和审计记录。
- 客户端密钥摘要、停用、到期、权限范围和换取短期令牌的相关模型/实现。
- CallerContext 中 UserId、AppCode 等用户上下文字段及部分用户令牌转换能力。

关键差异：

1. 当前主要对外入口使用匿名直连模式，创建 `IsDirectAccess=true`、`AllResources=true` 的调用上下文。
2. 当前 ExternalToolClientEntity 是系统客户端模型，没有绑定员工的 OwnerUserId。已有 client_credentials 令牌主要表达客户端身份，不能仅凭它判断“我的任务”。
3. 独立工作任务、任务附件和新业务角色还需按上一版独立模块方案落地。

因此建议新增受保护的工作任务 MCP 入口，例如 `/mcp/work-tasks`，使用独立的工具可见性/调用策略。仅复用 MCP 框架和通用审计，不继承匿名直连的授权方式。

必须同时阻止工作任务工具通过旧 `/mcp`、`/mcp/v2` 和等价外部 HTTP 工具入口匿名发现或调用。新地址加鉴权而旧工具注册表仍可调用，会破坏本人权限边界。

代码核对依据：`calmadmin/Program.cs`、`calmadmin/Controllers/ExternalTools/ExternalToolController.cs`、`ExternalToolTokenController.cs`、`Model/ExternalTools/ExternalToolEntities.cs`、`ExternalToolDtos.cs`、`Service/ExternalTools/ExternalToolService.cs`。

## 3. 两种连接方式

| 方式 | 员工体验 | 适用范围与限制 |
|---|---|---|
| 个人访问令牌/PAT | 在本系统创建凭证，将其配置到支持自定义 Authorization 请求头的 MCP 客户端 | 可作为一期兼容方式；属于应用接入约定，不能直接宣称是完整 OAuth 授权实现；部分客户端无法手填静态请求头 |
| OAuth 2.1 用户授权 | 在客户端点击连接，跳转本系统登录并授权，再取得面向工作任务服务的短期令牌 | 更适合标准远程 MCP 授权；需授权发现、PKCE、正确的 resource/audience 和令牌生命周期支持，并验证目标客户端兼容性 |

推荐先确定员工实际使用的客户端：支持手动请求头时可先提供个人令牌；目标客户端主要采用 OAuth 时，应优先实现 OAuth 用户授权。两种方式共用用户身份和业务权限。

MCP HTTP 授权规范定义了 OAuth 授权流程、逐请求携带令牌和目标资源校验。授权头的支持情况与文件处理能力需要按实际客户端验证，不把“支持 MCP”理解为所有接入功能完全一致。

## 4. 个人凭证与权限

建议建立个人凭证记录：KeyId、OwnerUserId、授权应用/任务工作区、允许操作、到期时间、密钥摘要、撤销/轮换版本、最近使用时间及客户端名称。每个客户端可使用不同凭证，便于单独撤销。

- 凭证由已登录且获准使用模块的本人创建，不能自行绑定其他员工或授予超过本人的业务权限。
- 明文只在创建时展示，服务端保存摘要；连接使用 HTTPS，请求和审计日志不记录完整密钥。
- 每次工具调用都解析服务端身份，并重新检查账号启用、凭证状态、当前模块授权和任务关系。
- 调用参数不接受可任意指定的汇报人 UserId。任务查询固定落到当前凭证所有者，替换 taskId、draftId、attachmentId 也不能越权。
- 员工主责、协作、关注关系分别控制读写。加入一项协作任务不等于能修改该任务所有内容或读取其他任务。
- 个人自助入口默认维持“本人相关任务”范围，即便此账号同时是主管，也不自动开放团队管理数据。团队查询、派发和验收应另行设计工具与授权范围。
- 有效授权是个人凭证范围、当前账号业务能力、任务关系及流程条件共同约束。`*`、AllResources 或普通客户端身份不能跳过职责限制。
- 账号停用、任务转派和授权撤销后，已有凭证也受当前权限限制；如果采用短期令牌，仍需设计在线撤销/版本检查，不能单靠等到令牌自然过期。
- MCP 凭证具有独立生命周期；后台查询不视为网页用户操作，不自动延长网页的 20 分钟空闲会话。

## 5. 建议一期开放的工具

工具名为设计示例，最终应按客户端兼容性和服务端命名规则确定。

| 工具示例 | 能力 | 业务限制 |
|---|---|---|
| `worktask.my.list` | 查询我的任务、待评估、节点、待补充和验收状态 | 只返回本人可见字段与范围，分页读取 |
| `worktask.my.get` | 查看某任务要求、节点和允许查看的反馈 | 直接访问任务 ID 仍校验身份 |
| `worktask.assessment.reply` | 回复可行性、预计开始、承诺节点和协调事项 | 仅当前获准评估的人操作；超出要求的排期进入待确认 |
| `worktask.progress.report` | 提交进展、文字说明和阻塞事项 | 仅获准办理的任务，不直接视为验收完成 |
| `worktask.deliverable.draft` | 创建或更新成果提交草稿 | 绑定本人、任务、当前版本和交付要求 |
| `worktask.attachment.begin/complete` | 申请上传并登记已验证文件，返回附件 ID | 受任务/草稿、上传者、大小、类型及有效期约束 |
| `worktask.deliverable.submit` | 将确认后的文字与附件提交给验收人 | 状态、任务版本、附件归属和幂等校验通过后进入待验收 |
| `worktask.report.status` | 查询之前的汇报/提交是否成功 | 返回本人可见的报告编号、状态和时间，帮助断线后确认结果 |

一期个人入口只做查询和员工侧办理。人员授权、替人下派、任意修改任务要求、验收通过和强制完成不默认开放。

不提供任意 SQL、通用文件系统路径访问、任意资源转发或未受约束的 HTTP 请求工具。

## 6. 文件和图片上传

文字汇报可以直接作为结构化工具参数传入。文件和图片需要专门的上传业务协议；MCP 的工具/图像内容支持不等于客户端已具备读取本地文件并上传的通用能力。

| 上传方式 | 建议用途 | 关键点 |
|---|---|---|
| MCP 工具参数携带受限 Base64 内容 | 小图片、小附件，且客户端确实能读取文件并构造参数 | 受大小限制，避免让模型手工生成或转抄大段编码；这是自定义上传工具 |
| MCP 申请上传会话，客户端经 HTTPS 上传二进制 | 常规文件和大附件，推荐的主方案 | 上传会话绑定任务、草稿、本人、允许文件和短有效期，完成后服务端验证再返回附件 ID |
| MCP 返回受控的浏览器上传入口 | 客户端只支持文字工具调用、不能发送文件内容时的兼容入口 | 员工在网页选择文件上传，再由 MCP 引用附件 ID 继续汇报 |

不能只传 `C:\...\照片.jpg` 就要求远端服务读取员工电脑文件。也不能把任意外部图片 URL 当作已保存成果；如以后支持链接材料，应与正式上传附件区分。

上传后使用附件 ID 关联正式汇报，服务端检查实际内容、大小、文件类型、上传完整性和归属。采用唯一文件键，旧提交材料不被同名新文件覆盖。未完成上传的文件不能提交验收，未关联的临时文件按策略清理。

下载与图片预览采用任务授权或受控短期访问，不把所有成果文件发布为永久公共链接。附件上传权限和附件内容交给模型读取的权限可分别控制。

## 7. 提交确认、重试和业务一致性

建议将“草稿/日常进展”与“正式承诺节点、延期申请、提交成果”区分：普通进展按授权直接记录，正式动作先给出结构化预览，由员工确认后调用提交工具。确认可在受支持的客户端完成，不要求每次重新登录网页。

注意：模型自动填入 `confirm:true` 本身不是可验证的真人确认。若业务要求证明真人批准，需要可信客户端确认或系统确认页面，并将确认与具体任务、草稿版本、附件集合绑定。

- 写入带唯一请求标识；相同请求重试返回同一个结果，同标识不同内容拒绝，避免重复汇报。
- 提交携带预期版本，任务转派、要求变化或并发编辑时拒绝过期操作，要求刷新后确认。
- 成果提交后进入待验收；个人凭证不能自行验收或跳过主管确认。
- 接口返回持久化汇报/提交编号、当前状态、服务器记录时间和可访问的详情入口。工具报成功必须意味着业务记录已落库，而非仅生成了一段文字。
- 断线或超时后先查询结果，再按原请求标识重试，避免因客户端未收到响应而重复提交。
- 网页和 MCP 共用工作任务服务。日报、即时通知和管理看板依据同一业务记录生成，不另造一套 MCP 状态。

## 8. 审计、通知和开放边界

汇报记录保存 OwnerUserId、KeyId/客户端、来源 MCP、任务/提交批次、请求标识、业务时间和结果。工具审计不记录原始密钥、文件 Base64 或不必要的全文。

员工通过 MCP 提交的进展、阻塞和成果纳入个人/领导摘要；需要验收的任务仍由原业务验收人处理。消息发送方身份和收件范围由任务规则确定，不让客户端任意指定领导或其他收件人。

对接云端 AI 客户端时，返回的任务文字及选定文件可能由该客户端和模型服务处理。应允许按公司规则限定可连接客户端、可返回字段与附件读取范围，避免一次连接自动获取全部历史材料。

部署时通过固定 HTTPS 入口代理受保护的工作任务 MCP 和上传服务。不能沿用旧“匿名内网直连”的开放方式承载个人工作汇报。

## 9. 实施顺序与验证

1. 按独立模块评估落地 WorkTask、业务角色、组织范围和统一流程服务。
2. 新增个人凭证管理、受保护 MCP 入口和个人查询/文字汇报工具，明确目标客户端。
3. 接入上传会话、附件验证和正式提交，再验证图片与文件的实际客户端能力。
4. 接入同一套日终摘要与投递队列，完成端到端试点。

建议验证场景（待开发后执行，本次未运行）：

- 员工 A 的凭证不能查询或修改员工 B 的任务、草稿和附件；伪造 UserId 不改变身份。
- 无凭证、撤销/到期凭证、停用账号和角色撤销不能继续办理。
- 已授权任务转派后旧执行人不能继续提交；主管自己的个人凭证不能自验收。
- 旧匿名 MCP/外部 HTTP 接口既不列出也不能调用工作任务工具。
- 图片、普通文件、空文件、超限文件、伪造格式、跨草稿附件、过期上传会话均按规则处理。
- 重复提交、提交响应丢失、同标识不同内容和过期版本都有确定结果。
- 无文件上传能力的客户端可以使用受控网页入口完成汇报。
- MCP 汇报与网页展示、领导摘要、员工摘要和通知记录一致。
- 不同 MCP 协议/授权客户端分别通过真实连接测试，不把某个客户端成功推断为全平台通用。
